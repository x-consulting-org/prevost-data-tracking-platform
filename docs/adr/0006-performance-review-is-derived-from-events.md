# The performance review is derived from shipment events

The Kollégák screen rates each dispatcher on facts the mailbox and T-Port already deliver: when a request arrived, when the first reply went out (`RESPONSE_SENT`), when a T-Port trip was linked, when T-Port reported the truck loaded and unloaded (`PICKED_UP`, `DELIVERED`), how often the schedule or details changed, and which vehicle carried each trip. `buildPerformanceReview(dispatchers, shipments, now, settings)` computes every metric and verdict from these on each read, like the alerts (ADR 0003), so there are no stored scores to fall out of step with the timeline. These moments are events rather than columns on the shipment, so the timeline stays the one record of what happened; `milestonesOf` reads them for the review and for the shipment cards alike, so a card shows the same first-reply time, trip time and truck turnaround that the review counts.

Dimensions the pilot cannot measure yet (partner relationships, the business quality of a trip choice, escalation, unnecessary internal rounds) are left out rather than estimated: they need email content analysis or a manager's assessment, and a number without data behind it would be worse than none. The thresholds (the review window, the ±% band for "on par", minimum samples, when a request is unanswered, how many changes count as repeated, how late is late) live in a single `MetricSettings` row rather than in code, because operations will tune them after the workshop. The Kollégák › Mérőszámok page shows each rule as a sentence with its number editable in place; a save carries the `updatedAt` it started from and is refused if someone saved in between. The cards, the alerts and the review all read the same row, so a change moves every screen at once.
